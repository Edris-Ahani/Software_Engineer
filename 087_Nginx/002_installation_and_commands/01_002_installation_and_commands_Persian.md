# 002 — نصب، مسیرها، اعتبارسنجی و بارگذاری امن

<div dir="rtl">

## هدف و محیط اجرا
روی یک ماشین آزمایشی Ubuntu/Debian بستهٔ توزیع را نصب کنید، مسیر واقعی تنظیمات را پیدا کنید و آن را امن بارگذاری کنید. دستورهای لینوکسی این مجموعه در Linux یا WSL اجرا می‌شوند و دستور PowerShell نیستند. روی ویندوز بدون سرویس‌منیجر لینوکس، آزمایشگاه Docker را اجرا کنید.

بستهٔ توزیع و بستهٔ nginx.org ممکن است کاربر اجرایی، ماژول‌ها، مسیر و فایل سرویس متفاوت داشته باشند. دستور نصب این دو روش را ترکیب نکنید. نمونهٔ زیر از مخزن توزیع نصب می‌کند؛ به‌روزرسانی امنیتی را نیز از همان مسیر دنبال کنید.

</div>


```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable --now nginx
nginx -v
nginx -V 2>&1
sudo nginx -t
sudo systemctl status nginx --no-pager
curl -I http://127.0.0.1/
```

<div dir="rtl">

## دستورها و دلیل استفاده

| دستور | کاربرد |
| --- | --- |
| `nginx -v` | نمایش نسخه |
| `nginx -V` | گزینه‌های ساخت و مسیرهای کامپایل‌شده |
| `nginx -t` | بررسی نحو و باز شدن فایل‌های ارجاع‌شده |
| `nginx -T` | بررسی و چاپ تنظیمات بارگذاری‌شده همراه includeها |
| `systemctl reload nginx` | درخواست بارگذاری تنظیمات جدید از سرویس موجود |
| `nginx -s quit` | خاموشی تدریجی برای نمونهٔ تحت مدیریت مستقیم |
| `nginx -s stop` | خاموشی سریع با احتمال قطع کار جاری |

خروجی `nginx -T` ممکن است تنظیمات محرمانهٔ داخل فایل را نشان دهد؛ قبل از اشتراک‌گذاری آن‌ها را حذف کنید. موفق شدن `-t` به معنی در دسترس بودن بک‌اند، تطابق گواهینامه با دامنه یا صحیح بودن منطق مسیریابی نیست.

</div>


```bash
# After editing the loaded configuration:
sudo nginx -t && sudo systemctl reload nginx
sudo journalctl -u nginx -n 30 --no-pager
sudo tail -n 30 /var/log/nginx/error.log
curl -i http://127.0.0.1/
```

## مسیرها و مجوزها
مسیرهای رایج `/etc/nginx/nginx.conf`، `/etc/nginx/conf.d/` و `/var/log/nginx/` هستند. بسته‌های خانوادهٔ Debian معمولاً `sites-enabled/` هم دارند؛ این پوشه قرارداد بسته‌بندی است و جزء اجباری Nginx نیست. فایل تا زمانی که از تنظیمات فعال include نشود اثری ندارد. مسیر را با `nginx -V` و `nginx -T` پیدا کنید.

در reload، workerهای قبلی فرصت اتمام درخواست‌های فعال را دارند و workerهای جایگزین با تنظیمات جدید شروع می‌شوند. WebSocket طولانی می‌تواند عمر worker قبلی را طولانی کند. وقتی systemd پورت ۸۰ را مدیریت می‌کند، یک Nginx دوم را دستی اجرا نکنید.

## خطای رایج و بازیابی
دستور ناشناخته می‌تواند ناشی از نبود ماژول یا ناسازگاری نسخه باشد. خطای مجوز ممکن است از نداشتن اجازهٔ عبور از یک پوشه یا خواندن کلید توسط master باشد. نام فایل و خط دقیق خطا را بخوانید. فایل سالم قبلی را برگردانید، `-t` بزنید، reload کنید و یک درخواست واقعی را امتحان کنید.

## تمرین و پاسخ
در یک تنظیمات آزمایشی دستور نامعتبر قرار دهید و `-t` بزنید. باید شکست بخورد؛ reload نکنید. بعد از حذف دستور، هم بررسی نحو و هم درخواست HTTP باید موفق شوند. این آزمایش را روی فایل زندهٔ تولید انجام ندهید.
