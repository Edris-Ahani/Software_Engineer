# 001 — معماری پردازش‌ها و مدل حافظه در PostgreSQL

## هدف یادگیری
آشنایی با معماری پردازش‌محور (Process-based) در PostgreSQL، نحوهٔ مدیریت اتصالات کلاینت، تفکیک پردازش‌های پس‌زمینه و ساختار حافظهٔ اشتراکی (Shared Memory). پیش‌نیاز: درک مفاهیم سیستم‌عامل نظیر حافظه اشتراکی، پروسس و ترد.

---

## ۱. نمای کلی معماری پردازش‌ها

برخلاف سیستم‌هایی چون MySQL یا MSSQL که بر پایه‌ی مدل چندنخی (Multi-threaded) طراحی شده‌اند، PostgreSQL از **مدل مبتنی بر پردازش (Process-based)** با ایزولاسیون کامل حافظه استفاده می‌کند. تمام پردازش‌ها از طریق حافظه اشتراکی و سمافورهای IPC سیستم‌عامل با یکدیگر هماهنگ می‌شوند.

```text
+-------------------------------------------------------------------------+
|                          Postmaster (Main Daemon)                       |
+-------------------------------------------------------------------------+
       |                  |                    |                  |
       v                  v                    v                  v
+--------------+   +--------------+     +--------------+   +--------------+
| Client Conn  |   | Client Conn  |     | Background   |   | Background   |
| Backend #1   |   | Backend #2   |     | Checkpointer |   | Background   |
| (OS Process) |   | (OS Process) |     | (OS Process) |   | Writer       |
+--------------+   +--------------+     +--------------+   +--------------+
       \                  /                    |                  |
        v                v                     v                  v
+-------------------------------------------------------------------------+
|                             SHARED MEMORY                               |
|  +--------------------+ +--------------------+ +---------------------+  |
|  |   Shared Buffers   | |    WAL Buffers     | |      CLOG/SLRU      |  |
|  +--------------------+ +--------------------+ +---------------------+  |
|  |                    Lock Manager & IPC Semaphores                  |  |
+-------------------------------------------------------------------------+
                                   |
                                   v
                      Physical Disk (Data & WAL)
```

### پردازش اصلی سرور (Postmaster)
هنگام روشن شدن سرویس، پردازش والد (`postgres`) اجرا می‌شود و وظایف زیر را به عهده دارد:
- تخصیص بلوک‌های حافظه اشتراکی و قفل‌های همگام‌سازی.
- راه‌اندازی پردازش‌های کمکی پس‌زمینه (`checkpointer`، `bgwriter`، `walwriter`، `autovacuum`).
- گوش دادن به پورت شبکه (پیش‌فرض ۵۴۳۲ TCP) و سوکت محلی Unix Domain Socket.
- اجرای عمل Fork برای ایجاد یک پردازش Backend اختصاصی به ازای هر اتصال کلاینت احراز هویت شده.

## ۲. پردازش‌های کلیدی پس‌زمینه

| نام پردازش | وظیفه اصلی | تأثیر در محیط پروداکشن |
| :--- | :--- | :--- |
| **Checkpointer** | نوشتن بافرهای تغییریافته (Dirty Pages) به دیسک در فواصل زمانی منظم (`checkpoint_timeout`). | ایجاد بار I/O سنگین در صورت عدم تنظیم دقیق پارامتر `checkpoint_completion_target`. |
| **Background Writer (bgwriter)** | تمیز کردن پیش‌دستانه‌ی بافرها در دسته‌های کوچک برای آماده‌سازی حافظه برای کوئری‌های بعدی. | کاهش تأخیر در نوشتن کوئری‌های کلاینت. |
| **WAL Writer** | تخلیه رکوردهای تغییرات از حافظه به فایل‌های فیزیکی لاگ قبل از اعمال (WAL). | تضمین پایدار بودن داده‌ها بر اساس اصول ACID هنگام Commit. |
| **Autovacuum Launcher** | پایش نسبت رکوردهای منقضی‌شده و راه‌اندازی فرآیند پاک‌سازی فضا. | جلوگیری از پر شدن دیسک (Bloat) و جلوگیری از خطر Transaction ID Wraparound. |
| **Stats Collector** | جمع‌آوری آمار مربوط به خواندن صفحات، اسکن ایندکس‌ها و تعداد سطرها. | ارسال اطلاعات حیاتی به موتور برنامه‌ریزی کوئری (Cost-based Query Planner). |

## ۳. معماری حافظه در PostgreSQL

حافظه به دو بخش اساسی تقسیم می‌شود: **حافظه اشتراکی (Shared Memory)** و **حافظه اختصاصی هر پردازش (Process-Local Memory)**.

```text
+-------------------------------------------------------------------------+
| کل مصرف حافظه (TOTAL RAM USAGE)                                         |
|                                                                         |
| [ فضای حافظه اشتراکی - Shared Memory Area ]                              |
| ├── shared_buffers       (حدود ۲۵ درصد از کل حافظه RAM سرور)           |
| ├── wal_buffers          (پیش‌فرض حدود ۱۶ مگابایت)                       |
| └── ساختارهای Lock Manager                                              |
|                                                                         |
| [ فضای حافظه اختصاصی هر سشن - Per-Backend Memory ]                      |
| ├── work_mem             (عملیات Sort، Hash و Merge به ازای هر عمل)     |
| ├── maintenance_work_mem (دستورات VACUUM، ساخت ایندکس و تغییرات جدول)  |
| └── temp_buffers         (جداول موقت سشن)                               |
+-------------------------------------------------------------------------+
```

> **فرمول حیاتی مدیریت حافظه:**
> $$\text{Peak RAM Usage} \approx \text{shared\_buffers} + (\text{max\_connections} \times \text{work\_mem} \times \text{operations\_per\_query})$$
> اگر پارامتر `work_mem` را بیش از حد بزرگ (مثلاً 64MB) تنظیم کنید و `max_connections` برابر 500 باشد، در صورت همزمانی کوئری‌های سنگین، سرویس OOM-Killer سیستم‌عامل کل پروسس دیتابیس را متوقف خواهد کرد!

## ۴. آزمایش عملی و بررسی زنده

برای مشاهده پردازش‌های زنده و پارامترهای حافظه، این دستورات را در `psql` اجرا کنید:

```sql
-- View all background and client processes
SELECT pid, backend_type, usename, client_addr, state, query
FROM pg_stat_activity
ORDER BY backend_type;

-- Inspect active memory configurations
SHOW shared_buffers;
SHOW work_mem;
SHOW maintenance_work_mem;
SHOW max_connections;
```

## ۵. تمرین سناریومحور و پاسخ

**صورت تمرین:**  
سروری با ۳۲ گیگابایت حافظه رم دارید و `max_connections` را روی ۴۰۰ و `work_mem` را روی 128MB تنظیم کرده‌اید. یک گزارش تحلیلی سنگین دارای ۳ عملیات مرتب‌سازی و هش مستقل در پلن اجرایی خود است. بیشترین حافظه اختصاصی که این یک کوئری می‌تواند مصرف کند چقدر است و چه خطری سیستم را تهدید می‌کند؟

**پاسخ:**  
هر گره مرتب‌سازی یا هش در پلن اجرایی به‌طور مستقل تا سقف `work_mem` حافظه تخصیص می‌دهد.
$3 \times 128\text{ MB} = 384\text{ MB}$ مصرف این تک‌کوئری خواهد بود.
اگر ۱۰۰ اتصال همزمان چنین کوئری را اجرا کنند:
$100 \times 384\text{ MB} = 38.4\text{ GB}$ که فراتر از حافظه فیزیکی ۳۲ گیگابایتی سرور است و سیستم با خطای Out of Memory مواجه می‌شود.  
*راهکار بهینه‌سازی:* مقدار سراسری `work_mem` را محافظه‌کارانه (مثلاً 8MB یا 16MB) نگه دارید و تنها در سشن‌های تحلیلی خاص با دستور `SET work_mem = '256MB';` آن را افزایش دهید.
