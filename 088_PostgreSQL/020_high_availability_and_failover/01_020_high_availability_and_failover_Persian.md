# 020 — معماری High Availability با Patroni و etcd

## هدف یادگیری
طراحی و پیاده‌سازی خوشه‌های در دسترس‌پذیری بالا (HA) برای PostgreSQL؛ درک متریک‌های RPO و RTO، پیشگیری از فاجعه دوپارگی مغز (Split-Brain) با الگوریتم‌های اجماع توزیع‌شده (etcd/Raft) و پیاده‌سازی سوییچ خودکار (Failover) با **Patroni** و **HAProxy**.

---

## ۱. شاخص‌های سنجش دسترسی‌پذیری بالا: RPO و RTO

- **نقطه هدف بازیابی (RPO):** حداکثر میزان داده قابل‌قبول برای از دست رفتن که بر حسب زمان سنجیده می‌شود (مثلاً RPO = 0 یعنی حتی یک تراکنش کامیت‌شده نباید از بین برود).
- **زمان هدف بازیابی (RTO):** حداکثر زمان مجاز خاموشی سیستم تا بازگشت کامل سرویس به مدار (مثلاً RTO زیر ۳۰ ثانیه).

---

## ۲. فاجعه دوپارگی مغز (Split-Brain)

دوپارگی مغز زمانی رخ می‌دهد که قطعی موقت در شبکه ارتباطی بین سرورها رخ دهد و دو سرور مجزا هر دو به اشتباه تصور کنند سرور اصلی (Primary) هستند:

```text
[ بروز قطعی در سوییچ شبکه ]
کلاینت‌های دیتاسنتر اول ───> سرور Primary الف (تراکنش‌های جدید را ثبت می‌کند)
                                       X (قطع ارتباط بین سرورها)
کلاینت‌های دیتاسنتر دوم ───> سرور Standby ب به Primary ارتقا یافته (تراکنش‌ها را ثبت می‌کند)
```
**پیامد فاجعه‌بار:** هر دو سرور خطوط زمانی مجزایی برای WAL تولید می‌کنند (`Timeline 2` در سرور اول در برابر `Timeline 2` در سرور دوم). داده‌های دیتابیس‌ها از یکدیگر واگرا شده و ادغام خودکار آن‌ها از نظر ریاضی ناممکن خواهد بود!

### راهکار علمی: حد نصاب اکثریت (Quorum Consensus)
فرآیند ارتقای خودکار هرگز نباید با پینگ ساده بین دو سرور انجام شود. الزامی است از یک ذخیره‌ساز اجماع توزیع‌شده مثل **etcd** با **تعداد فرد نودها** (حداقل ۳ نود بر پایه الگوریتم Raft) استفاده شود تا شرط اکثریت مطلق ($N/2 + 1$) رعایت شود.

---

## ۳. معماری استاندارد صنعتی Patroni

پاترونی یک ناظر و سوپروایزر هوشمند به زبان پایتون است که بر مبنای etcd وضعیت کلاستر PostgreSQL را مدیریت می‌کند:

```text
                           +----------------------+
                           |   برنامه‌ها و کلاینت‌ها|
                           +----------------------+
                                      │
                                      v
                           +----------------------+
                           |   HAProxy / VIP      |
                           +----------------------+
                            /        │         \
      تست سلامت پورت ۸۰۰۸  /         │          \  تست سلامت پورت ۸۰۰۸
         (مسیر primary/)  /          │           \   (مسیر replica/)
                         v           v            v
                 +------------+ +------------+ +------------+
                 |  نود اول   | |  نود دوم   | |  نود سوم   |
                 | (Primary)  | | (Standby)  | | (Standby)  |
                 |  Patroni   | |  Patroni   | |  Patroni   |
                 | PostgreSQL | | PostgreSQL | | PostgreSQL |
                 +------------+ +------------+ +------------+
                         \           │            /
                          \          │           /
                           v         v          v
                 +------------------------------------------+
                 |        کلاستر ذخیره‌ساز اجماع توزیع‌شده    |
                 |             (کلاستر ۳ نودی etcd)         |
                 +------------------------------------------+
```

### چرخه اجرای سوییچ خودکار (Failover):
۱. نود Primary قفل لیدر را با یک مهلت کوتاه (TTL ۱۰ ثانیه‌ای) در etcd ثبت می‌کند.
۲. پروسس Patroni روی نود اصلی هر ۲ ثانیه این اجاره را تمدید می‌کند.
۳. در صورت کرش کردن سرور اصلی، اجاره آن در etcd منقضی می‌شود.
۴. سرورهای Standby باقی‌مانده موقعیت LSN خود را مقایسه می‌کنند و سروری که **کمترین تأخیر رپلیکیشن** را دارد قفل لیدر جدید را دریافت می‌کند.
۵. پاترونی سرور برگزیده را به Primary ارتقا می‌دهد.
۶. لودبالانسر HAProxy از طریق پایش مداوم متوجه می‌شود که نود دوم پاسخ `HTTP 200` در مسیر `/primary` می‌دهد و ترافیک نوشتن برنامه‌ها را در کمتر از ۵ ثانیه به نود جدید منتقل می‌کند!

## ۴. اتصال HAProxy با REST API داخلی Patroni

پاترونی روی پورت ۸۰۰۸ یک وب‌سرویس اعلام وضعیت ارائه می‌دهد:
- مسیر `GET http://node:8008/primary` -> در صورتی که نود لیدر اصلی باشد کد ۲۰۰ و در غیر این صورت ۵۰۳ می‌دهد.
- مسیر `GET http://node:8008/replica` -> در صورت آماده‌به‌کار بودن Standby کد ۲۰۰ برمی‌گرداند.

### فایل پیکربندی نمونه در HAProxy (`haproxy.cfg`):
```haproxy
listen postgres_write_pool
    bind 0.0.0.0:5000
    mode tcp
    option httpchk GET /primary
    http-check expect status 200
    default-server inter 3s fall 3 rise 2 on-marked-down shutdown-sessions
    server pg1 10.0.1.11:5432 maxconn 100 check port 8008
    server pg2 10.0.1.12:5432 maxconn 100 check port 8008
    server pg3 10.0.1.13:5432 maxconn 100 check port 8008

listen postgres_read_pool
    bind 0.0.0.0:5001
    mode tcp
    balance roundrobin
    option httpchk GET /replica
    http-check expect status 200
    server pg1 10.0.1.11:5432 check port 8008
    server pg2 10.0.1.12:5432 check port 8008
    server pg3 10.0.1.13:5432 check port 8008
```

## ۵. تمرین سناریومحور و پاسخ

**صورت تمرین:**  
یک کلاستر ۲ نودی دارید و اسکریپتی نوشته‌اید که اگر نود ۲ به مدت ۵ ثانیه پاسخی از نود ۱ دریافت نکرد، نود ۲ را به عنوان Primary معرفی کند. چرا این معماری به‌شدت خطرناک است؟

**پاسخ:**  
یک کلاستر ۲ سروره قادر به تشکیل حد نصاب اکثریت (Quorum) نیست. اگر به دلیل قطعی چندثانیه‌ای سوییچ شبکه ارتباط بین دو سرور قطع شود، نود ۲ به اشتباه فکر می‌کند نود ۱ مرده است و خود را لیدر می‌کند؛ در حالی که نود ۱ زنده است و کلاینت‌ها همزمان در هر دو سرور داده می‌نویسند (**Split-Brain**). برای پیشگیری از این فاجعه حتماً باید حداقل ۳ نود در فرآیند اجماع (Consensus) شرکت داشته باشند.
