# 007 — مکانیزم چندنسخه‌ای MVCC، عملیات واکیوم و پدیده Bloat

## هدف یادگیری
درک عملکرد هستهٔ سیستم کنترل همزمانی چندنسخه‌ای (MVCC)، ساختار هدر سطرها (`xmin`، `xmax`، `ctid`)، هزینه واقعی دستور `UPDATE`، بهینه‌سازی Heap-Only Tuples (HOT) و تنظیم پارامترهای Autovacuum جهت جلوگیری از باد کردن دیتابیس (Bloat).

---

## ۱. عملکرد داخلی سیستم MVCC

در PostgreSQL، **خوانندگان هرگز منتظر نویسندگان نمی‌مانند و نویسندگان مانع خواندن نمی‌شوند**. برای رسیدن به این قابلیت، به‌جای بازنویسی درجا (In-place Mutation)، به ازای هر ویرایش یک نسخه فیزیکی جدید از سطر در صفحه دیسک ذخیره می‌شود:

```text
صفحه فیزیکی دیسک (۸ کیلوبایت)
+-------------------------------------------------------------------------------+
| هدر صفحه    | نشانگرهای سطر [LP1, LP2, ...] ───┐                              |
+------------------------------------------------│------------------------------+
|                                                v                              |
| نسخه سطر اول (سطر اولیه):                      نسخه سطر دوم (سطر ویرایش‌شده): |
| - xmin: 501 (تولید توسط تراکنش ۵۰۱)            - xmin: 504 (تولید توسط ۵۰۴)   |
| - xmax: 504 (حذف/ویرایش توسط ۵۰۴)              - xmax: 0   (زنده و معتبر)     |
| - ctid: (0, 2) [اشاره‌گر به نسخه جدیدتر سطر]   - ctid: (0, 2)                 |
| - مقدار: status = 'PENDING'                    - مقدار: status = 'PAID'       |
+-------------------------------------------------------------------------------+
```

### هزینه واقعی دستور `UPDATE`
هنگامی که دستوری نظیر `UPDATE` را اجرا می‌کنید:
۱. دیتابیس یک سطر کاملاً جدید با مقادیر تازه در صفحه درج می‌کند.
۲. فیلد `xmax` سطر قبلی را برابر با شناسه تراکنش فعلی قرار می‌دهد تا منقضی شود.
۳. پس از اتمام تراکنش‌های خواننده‌ای که در حال دیدن وضعیت قبلی بودند، سطر اولیه تبدیل به **Dead Tuple** (سطر مرده و باطله) می‌شود.

---

## ۲. بهینه‌سازی Heap-Only Tuples (HOT)

در حالت عادی، تغییر یک سطر مستلزم ساخت یک ورودی جدید در تک‌تک ایندکس‌های آن جدول است.  
تکنیک **HOT** زمانی فعال می‌شود که:
۱. هیچ‌کدام از ستون‌های ایندکس‌شده در دستور `UPDATE` تغییر نکرده باشند.
۲. صفحه فیزیکی جاری فضای خالی کافی برای میزبانی نسخه جدید سطر در **همان صفحه ۸ کیلوبایتی** را داشته باشد.

```sql
-- Reserve 20% free space per page specifically for fast HOT updates
ALTER TABLE store.orders SET (fillfactor = 80);
```

مشاهده نسبت آپدیت‌های بهینه HOT در محیط عملیاتی:
```sql
SELECT relname,
       n_tup_upd,
       n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 2) AS hot_ratio_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 1000;
```

## ۳. تفاوت `VACUUM` معمولی با `VACUUM FULL`

| ویژگی | دستور استاندارد `VACUUM` | دستور سنگین `VACUUM FULL` |
| :--- | :--- | :--- |
| **سطح قفل** | `SHARE UPDATE EXCLUSIVE` (اجازه خواندن و نوشتن همزمان). | `ACCESS EXCLUSIVE` (**قفل کامل جدول؛ توقف تمام خواندن‌ها و نوشتن‌ها**). |
| **بازپس‌گیری فضا** | اسلات‌های مرده را برای درج‌های آینده جدول علامت‌گذاری می‌کند. حجم فایل دیسک سیستم‌عامل را کوچک نمی‌کند. | کل جدول را در یک فایل فیزیکی تازه بازنویسی می‌کند و فضای خالی را به سیستم‌عامل پس می‌دهد. |
| **کاربرد در پروداکشن** | به‌صورت پیوسته در پس‌زمینه توسط Autovacuum اجرا می‌شود. | به علت قطعی سرویس در پروداکشن خطرناک است. باید از ابزار بدون قطعی `pg_repack` استفاده شود. |

---

## ۴. فرمول تنظیم بهینه Autovacuum

تنظیمات پیش‌فرض Autovacuum برای حجم کاری بالای دیتابیس‌های امروزی بسیار تنبل است:

```ini
# Production adjustments in postgresql.conf
autovacuum_max_workers = 5
autovacuum_vacuum_cost_limit = 2000     # Increase from default 200 to allow faster I/O
autovacuum_vacuum_cost_delay = 2ms      # Throttle pause

# Default trigger formula:
# Dead tuples needed = autovacuum_vacuum_threshold + (autovacuum_vacuum_scale_factor * table_rows)
```

در جداول پرحجم (مثلاً ۵۰ میلیون سطر)، مقدار پیش‌فرض ۲۰٪ بدین معنی است که تا زمانی که **۱۰ میلیون رکورد باطله انباشته نشود**، پردازش پاک‌سازی بیدار نخواهد شد! تنظیم تهاجمی‌تر برای جداول با تراکنش بالا:

```sql
ALTER TABLE store.orders SET (
    autovacuum_vacuum_scale_factor = 0.02,  -- Trigger at 2% dead rows
    autovacuum_vacuum_threshold = 5000
);
```

## ۵. تمرین سناریومحور و پاسخ

**صورت تمرین:**  
جدولی با ۱۰ میلیون رکورد ۱۰ گیگابایت فضا روی دیسک دارد. پس از اجرای دستور `DELETE` روی ۸ میلیون رکورد و اجرای دستور `VACUUM`، حجم فایل فیزیکی دیسک در دستور `ls -lh` همچنان ۱۰ گیگابایت نمایش داده می‌شود. آیا عملیات شکست خورده است؟

**پاسخ:**  
خیر. دستور معمولی `VACUUM` اسلات‌های خالی را در جدول نقشه فضای آزاد (Free Space Map) به عنوان فضای قابل استفاده مجدد ثبت می‌کند تا `INSERT`های بعدی بدون نیاز به افزایش حجم فایل دیسک از آن استفاده کنند. برای بازگرداندن فیزیکی بایت‌ها به سیستم‌عامل بدون از دسترس خارج شدن سیستم، باید از ابزار `pg_repack` استفاده شود.
