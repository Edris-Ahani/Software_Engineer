# پروژهٔ ۰۰۲ ـ مدیریت موجودی و محاسبهٔ مبلغ

[بازگشت به دوره](../../README_Persian.md) · [تست رفتار](../../lessons/014_testing_Persian.md)

هدف: مدل‌کردن منطق کسب‌وکار بدون وابستگی به HTTP، فایل یا دیتابیس. یک SKU باید یکتا و دارای ۱ تا ۴۰ حرف/عدد ASCII یا خط تیره باشد. quantity رزرو باید مثبت باشد و مجموع مبلغ نباید overflow کند. قیمت در کوچک‌ترین واحد پولی یعنی سنت ذخیره می‌شود.

از ریشهٔ دوره:

```bat
cmd /c cargo run -p inventory
cmd /c cargo test -p inventory --offline
```

خروجی demo:

```text
Reserved 2 books for 3500 cents
Remaining: 3
```

## چرا ترتیب عملیات مهم است؟

`reserve` ابتدا quantity و وجود محصول، سپس موجودی و `checked_mul` مبلغ را بررسی می‌کند؛ تنها پس از تمام این کنترل‌ها موجودی کم می‌شود. اگر ابتدا موجودی را کم و بعد مبلغ را محاسبه کنیم، overflow می‌تواند عملیات را نیمه‌کاره بگذارد.

در `add` از API نوع entry روی BTreeMap استفاده شده تا duplicate، محصول موجود را overwrite نکند. getter فقط reference خواندنی می‌دهد؛ مصرف‌کننده نمی‌تواند مستقیماً موجودی private را دست‌کاری کند.

[پیاده‌سازی دامنه](src/lib.rs) خطاهای typed دارد. [تست‌ها](tests/reservations.rs) علاوه بر خطا، ثابت‌ماندن stock در overselling، overflow و duplicate را بررسی می‌کنند؛ حالت رزرو دقیق تمام موجودی نیز پوشش داده شده است.

## مرز واقعی نمونه

رزرو در این نسخه فوراً موجودی را کم می‌کند؛ expiration، لغو، پرداخت و event ندارد. قیمت صفر مجاز است و محصول رایگان را نشان می‌دهد. مقادیر پولی صرفاً یک واحد ثابت‌اند و این مدل multi-currency نیست. داده‌ها in-memory و تک‌فرایندی‌اند؛ transaction دیتابیس یا consistency چند replica پیاده نشده است.

برای توسعه، ابتدا قرارداد رزرو چندقلمی همه‌یا‌هیچ را تعریف کن. سپس adapter ذخیره‌سازی اضافه کن و API عمومی دامنه را مستقل از framework نگه دار. تست خطا نباید فقط Err بودن را بررسی کند؛ state بعد از خطا معیار اصلی است.
