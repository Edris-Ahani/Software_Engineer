# مقایسه gRPC و REST

## مشکلِ REST چیست؟
معماری REST استانداردِ بی‌چون‌وچرای APIهای وب است و از فرمت JSON بر روی پروتکل HTTP/1.1 استفاده می‌کند.
اما برای ارتباطات داخلی بین مایکروسرویس‌ها، REST معایبی دارد:
۱. **حجم بالای JSON**: فرمت JSON مبتنی بر متن (Text-based) است. سرور باید براکت‌ها را پارس کند و نوع داده‌ها را تبدیل کند (مثلاً رشته `"123"` را به یک عدد صحیح تبدیل کند). این کار کُند است و پردازنده (CPU) را هدر می‌دهد.
۲. **نبود قرارداد سخت‌گیرانه (Strict Contract)**: در REST، شما دقیقاً نمی‌دانید ساختار JSONِ دریافتی چه شکلی است، مگر اینکه از ابزارهای جانبی مانند Swagger (OpenAPI) استفاده کنید.

## ورود gRPC به میدان
فریم‌ورک gRPC که توسط گوگل ساخته شده، یک چارچوبِ مدرن و با کاراییِ بسیار بالا است که مشخصاً برای ارتباطات داخلیِ مایکروسرویس‌ها طراحی شده است.

۱. **پروتکل بافر (Protocol Buffers / Protobuf)**: به جای JSON، در gRPC از Protobuf استفاده می‌شود. شما ساختار داده‌های خود را در یک فایل `.proto` تعریف می‌کنید. سپس gRPC این داده‌ها را به فرمت باینری (صفر و یک) تبدیل می‌کند. فرمت باینری فوق‌العاده کم‌حجم است، به سرعت منتقل می‌شود و تقریباً نیازی به پردازش و پارس کردن توسط CPU ندارد.
۲. **قراردادهای سخت‌گیرانه**: فایل `.proto` به عنوان یک قراردادِ قطعی و غیرقابل نقض بین کلاینت و سرور عمل می‌کند و کدهای کلاینت را به صورت خودکار در هر زبانی (Go، پایتون، جاوا، Node.js) تولید (Auto-generate) می‌کند.
۳. **استفاده پیش‌فرض از HTTP/2**: معمولاً REST از HTTP/1.1 (یک درخواست در هر اتصال) استفاده می‌کند. اما gRPC بر پایه HTTP/2 بنا شده است که از Multiplexing (ارسال همزمانِ چندین درخواست موازی روی یک اتصال TCP) و استریم‌های دوطرفه (Bidirectional Streaming) پشتیبانی می‌کند.

## کدام را کی استفاده کنیم؟
- **REST**: برای APIهای عمومی و خارجی، مرورگرهای وب و اپلیکیشن‌های موبایل. مرورگرها هنوز پشتیبانیِ کاملی از gRPC خام ندارند.
- **gRPC**: منحصراً برای ارتباطات داخلی (Backend-to-Backend) بین مایکروسرویس‌ها، جایی که سرعت بالا، تاخیر پایین و ایمنیِ نوع داده‌ها (Type-Safety) به شدت حیاتی است.
